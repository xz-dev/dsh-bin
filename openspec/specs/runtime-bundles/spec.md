# runtime-bundles Specification

## Purpose

让 dsh 的可运行产物可以独立于管理器构建、发布和使用，同时通过明确的启动协议接受选定快照、应用 home 与 addon。隔离管理策略和必要运行适配，确保旧版本运行包不会带回旧管理器，新管理器也不需要重打包全部应用。

## Requirements

### Requirement: 运行包不携带管理引擎

运行包 SHALL 包含 dsh、其内嵌 Bun/pnpm、依赖及必要运行适配，MUST NOT 包含管理器可执行文件或负责下载、版本选择、快照创建/删除、自更新的管理引擎。构建一个运行包 MUST NOT 要求构建当前管理器。独立运行其应用入口时不得冒充管理器处理 `manager` 命令。

#### Scenario: RB-CONTENTS 独立检查运行包
- **WHEN** 构建并检查新的运行包及其入口依赖
- **THEN** 产物不包含管理器，也不包含可执行的管理命令分发逻辑；应用能在没有系统 Node/Bun 的环境中启动

### Requirement: 兼容性由格式与启动协议表达

运行包 SHALL 声明格式版本、运行包身份、上游来源、平台、启动协议和所需内容，不以某个管理器发行版本号相等作为兼容条件。管理器 SHALL 在激活和启动前验证兼容性；旧耦合格式、不支持的协议和缺失必需内容 MUST 明确拒绝，不能尝试执行旧 bundle 的管理代码进行转换。

#### Scenario: RB-INDEPENDENT 同一运行包配合不同管理器
- **WHEN** 两个独立发布的管理器支持同一启动协议并启动同一运行包
- **THEN** 无需重新构建该运行包，双方均能按协议启动它

#### Scenario: RB-LEGACY 拒绝旧格式
- **WHEN** 安装源提供旧的 launcher 与 bundles 混合归档
- **THEN** 管理器报告不支持的格式，不执行归档中的程序、不迁移用户数据

### Requirement: 应用仅消费已确定的启动环境

受管理的运行包 SHALL 消费管理器提供的运行包、快照、应用 home、addon 与缓存位置，不自行重新选择 latest、创建快照或回退到其他安装。快照插件文件和应用 home 中的共享配置 SHALL 分别使用明确传入的位置，不能根据快照目录的父级层数推断共享配置目录。

#### Scenario: RB-HOME 快照与应用 home 分离
- **WHEN** 管理器传入其数据根内的快照以及外部 DSH_HOME
- **THEN** 插件运行文件取自该快照，共享配置、凭据和会话取自指定应用 home，不写错误的相邻 profiles 目录

### Requirement: 重启保持当前运行上下文

应用内重启 SHALL 保持当前运行包、快照和 addon 的已解析选择，而不是重新读取用户此后修改的默认选择。受管理的 runtime 进程 SHALL 在生存期保护其运行包和快照，即使 Windows 上的管理器等待进程提前退出，也不能因此将仍运行的 runtime 视为可删除。该保护不扩展为对任意孤立子进程的保证。

#### Scenario: RB-RESTART 改默认选择不改变已有会话
- **WHEN** 会话使用 A/S，用户把默认选择改为 B，然后会话内部重启
- **THEN** 重启仍使用 A/S，B 只影响新的普通启动，A/S 的使用保护仍有效

### Requirement: 运行包更新由管理器拥有

受管理运行包 SHALL 保持只读，应用的上游自更新路径 MUST NOT 替换受管理运行包或管理器。插件安装仍由 dsh 在指定快照内执行；管理器只存储和选择快照，不替应用自动修复插件依赖。

#### Scenario: RB-PLUGIN 插件安装不修改应用映像
- **WHEN** 用户通过受管理 dsh 安装真实插件
- **THEN** 插件进入所选快照，运行包文件内容和管理器版本不变

### Requirement: 固定 CLI 补全描述随运行包发布

运行包 SHALL 提供带格式版本的固定 CLI 补全描述，描述 MUST 是数据而不是可执行 shell 代码。管理器可以读取该描述而无需启动 dsh。运行时插件动态增加的命令不属于此描述的保证；未知描述版本不得诱使管理器运行代码探测。

#### Scenario: RB-COMPLETION 描述与实际固定 CLI 一致
- **WHEN** 验收某一运行包的固定 CLI 命令和选项
- **THEN** 其补全描述对应该版本可用的固定命令和选项，而非另一版本的命令集合
